# CineRelay v0.2.7 — notification RCA recovery

## Scope

- Production RCA: oldest 100 due rows belonged to a user with no active FCM device; SQL applied LIMIT before active-device eligibility, starving newer records.
- Queue materializer selects eligible (delivery, device) pairs **before LIMIT**, excluding already-materialized targets; 24-hour freshness limit.
- One-time migration suppresses older outstanding alerts past 10 minutes to avoid a release-triggered push flood. Original rows and evidence remain retained.
- Recurring bounded expiry suppresses stale pending alerts after 24 hours. Never reinterpret quiet-hour delays as a fresh event.
- Maintenance findings refresh every 15 minutes so stale October 1 warning snapshots are not treated as current.
- OTT detail fetch without an explicit premiere date becomes a healthy, non-promoting "no date confirmed" check; connection/parser failures remain errors. No speculative OTT date is published.
- Database tests exercise >100 undeliverable rows ahead of one eligible row, target idempotency, TTL suppression, RPC privilege boundary, and scheduled jobs.

## Release and verification gates

1. Run GitHub CineRelay CI (pgTAP migration tests + db lint), Edge type-checks, and Android CI on the PR branch.
2. Review one-time backlog suppression SQL and verify outstanding fresh notifications are bounded before migration.
3. Apply migration to production only after green tests, inspect pending/suppressed/targets and cron health, and check new eligible test events end-to-end.
4. Deploy tested OTT worker bundle independently only after Edge CI. Verify no-explicit-date source health becomes healthy without inventing an OTT record.
5. Do not claim physical device notifications are delivered until an actual Android handset receives one and can open the correct deep link.
6. No Android version bump is necessary for this server-side change; retain the stable v0.2.6 APK until a true Android regression release.

## Rollback

- If regression observed, pause source-activity-push cron first, then restore earlier materializer function definition through a reviewed migration.
- One-time suppression is intentionally audit-preserving but not automatically reversible: it represents expired notifications and should **not** be resent en masse on rollback.
- Pause new maintenance/expiry cron jobs if unintended load occurs; retain the findings ledger.
